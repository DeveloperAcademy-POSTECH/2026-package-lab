# Swift Package Manager와 회귀 테스트

## 회귀 테스트란?

회귀 테스트란?
회귀 테스트는 단위 테스트나 통합 테스트처럼 별도의 테스트 단계라기보다, 코드를 변경한 뒤 기존 동작이 유지되는지 확인하려는 테스트의 목적이다.
- 단위 테스트: 하나의 함수·타입이 기대대로 동작하는지 확인
- 통합 테스트: 여러 기능이 함께 연결됐을 때 정상 동작하는지 확인
- 회귀 테스트: 수정 전 정상 동작하던 기능이 수정 후에도 유지되는지 확인
즉, 단위 테스트나 통합 테스트도 기존 동작의 재발 방지에 사용한다면 회귀 테스트가 될 수 있다.
회귀 버그란 이전에는 정상적으로 동작하던 기능이 코드 변경 이후 다시 깨지는 문제다.

## 기존 코드

SPM에서는 실제 라이브러리와 테스트가 서로 다른 Target으로 분리됨

```swift
.testTarget(
    name: "DiscountKitTests",
    dependencies: ["DiscountKit"]
)
```

테스트 Target은 DiscountKit을 가져와, 외부 사용자의 관점에서 공개 API가 약속대로 동작하는지 검증한다.

- `DiscountKit`: 상품 가격과 할인율을 받아 최종 가격을 계산해주는 패키지

```swift
public struct DiscountCalculator {
    public init() {}
    
    public func finalPrice(price: Int, discountRate: Double) throws -> Int {
        guard price >= 0 else {
            throw DiscountError.invalidPrice
        }
        
        guard (0...1).contains(discountRate) else {
            throw DiscountError.invalidDiscountRate
        }
        
        return Int(Double(price) * (1 - discountRate))
    }
}
```

- `DiscountKitTests`: `DiscountKit`의 동작을 검증하기 위해 작성한 테스트
10,000원에 20% 할인을 적용했을 때 8,000원이 나오는지를 검증

```swift
import Testing
@testable import DiscountKit

@Test("20% 할인")
func appliesTwentyPercentDiscount() async throws {
    let calculator = DiscountCalculator()
    
    let result = try calculator.finalPrice(price: 10000, discountRate: 0.2)
    
    #expect(result == 8000)
}
```

## 새로운 기능 추가

서비스에 새로운 요구사항이 생겼다면?

> 요구된 기능: VIP 회원에게는 기존 할인에 추가로 10% 할인을 더 받게 해주세요.
> 
- 기존 `finalPrice`에 `membership`이라는 파라미터를 추가

```swift
public struct DiscountCalculator {
    public init() {}
    
    public func finalPrice(
        price: Int,
        discountRate: Double,
        membership: Membership = .regular
    ) throws -> Int {
        guard price >= 0 else {
            throw DiscountError.invalidPrice
        }
        
        guard (0...1).contains(discountRate) else {
            throw DiscountError.invalidDiscountRate
        }
        
        let additionalRate = 0.1
        let finalDiscountRate = discountRate + additionalRate
        
        return Int(Double(price) * (1 - finalDiscountRate))
    }
}
```

- 새 기능이 제대로 동작하는지 새로운 테스트로 검증

```swift
@Test("VIP 회원은 추가 10%할인")
func vipGetsAdditionalTenPercentDiscount() throws {
    let calculator = DiscountCalculator()
    
    let result = try calculator.finalPrice(price: 10000, discountRate: 0.2, membership: .vip)
    
    #expect(result == 7000)
}
```

## 기존 테스트 실패

새로운 VIP 기능을 테스트했을 때는 정상적으로 통과하지만,

기존에 작성된 20% 할인 테스트는 실패

일반 회원도 추가 할인을 받게 되는 문제 생김

→ 새로운 기능은 정상적으로 구현, 기존 기능은 망가짐

## 코드 개선

- 문제를 해결하기 위해 회원 등급에 따라 추가 할인율을 다르게 적용하도록 수정

```swift
let additionalRate = membership == .vip ? 0.1 : 0
```

VIP라면 10%의 추가 할인을 적용하고, 일반 회원이라면 추가 할인을 적용하지 않도록 구현

→ 모든 테스트 통과

✅ 여기서 중요한 점! **새로운 기능을 추가하면서 기존 기능이 깨졌다는 사실을 테스트를 통해 바로 발견해버림**

## `@testable`이란?

일반적으로 Swift의 `internal` 접근 수준은 같은 모듈 내부에서만 접근할 수 있음

테스트 코드에서 `@testable`을 사용하면, 테스트 대상 모듈의 `internal` 선언에 접근할 수 있게 됨

**외부에 공개하지 않은 내부 구현도 테스트할 수 있도록 테스트 모듈에서 접근 범위를 확장해주는 역할**

그래서 내 코드에선 사실 없어도 됨

## SPM에서 회귀 테스트가 특히 중요한 이유

Swift Package는 여러 앱이나 다른 패키지가 가져다 쓰는 공개 API를 가진 라이브러리, 따라서 패키지 개발자는 새 버전을 배포할 때 기존 사용자의 코드를 깨뜨리지 않아야 함

- 소스 호환성: 기존 함수에 기본값 없는 파라미터를 추가하여 기존 호출 코드가 컴파일되지 않음
- 동작 호환성: 기존 호출 코드는 컴파일되지만 결과가 8,000원에서 7,000원으로 바뀜

- 패키지는 하나의 독립적인 기능 단위로 분리되어 있기 때문에 **패키지 내부의 코드를 수정하거나 버전을 업데이트했을 때 기존 기능이 정상적으로 동작하는지 테스트하기 좋음**
- 패키지의 기능이 여러 프로젝트에서 사용되고 있다면 작은 코드 변경 하나가 프로젝트들에게 큰 영향을 줌

이번 예시에서 membership: Membership = .regular는 기존 호출 코드가 계속 컴파일되도록 해 준다. 즉, 소스 호환성은 지켰다.
하지만 잘못된 구현은 일반 회원의 계산 결과를 조용히 바꿨다. 이런 컴파일은 되지만 동작이 달라지는 문제는 컴파일러가 잡을 수 없고, 회귀 테스트가 잡아야 한다.
이 점이 SPM 패키지에서 회귀 테스트가 특히 중요한 이유다.

즉 변경 안정성을 높이는 데 유용

## 회귀 테스트의 효능

### ① 기존 기능의 손상을 빠르게 발견할 수 있다

새로운 기능을 추가하면서 기존 기능이 깨지는 상황을 테스트를 통해 바로 발견 가능

### ② 코드 수정에 대한 심리적 부담을 줄여준다

기존 기능을 일일이 수동으로 확인하지 않아도 테스트를 실행해서 기존 동작이 유지되고 있는지 확인할 수 있음

### ③ 패키지의 안정성을 유지할 수 있다

패키지를 수정하거나 버전을 업데이트할 때 기존 기능이 유지되는지 지속적으로 검증할 수 있음

## 버전 관리와 연결하기

SPM 패키지는 보통 Semantic Versioning을 사용한다.

- PATCH: 기존 API와 동작을 유지한 버그 수정
- MINOR: 기존 사용법을 깨지 않는 기능 추가
- MAJOR: 기존 사용 코드를 깨는 변경

기본값 없이 새 파라미터를 추가했다면 기존 호출 코드가 컴파일되지 않으므로, 일반적으로 Major 버전을 올려야 하는 변경이다.
반면 이번 예시는 기본값 덕분에 호출 방식은 유지됐다. 하지만 일반 회원의 결과가 바뀌었다면 사용자의 기대를 깨는 변경이다. 회귀 테스트는 이런 동작 호환성 문제를 배포 전에 찾아낸다.

## 끝으로..

SPM에서 패키지는 버전이 붙은 공개 API로 배포된다. 컴파일러는 호출 방식이 깨지는 문제를 잡아 주지만, 컴파일은 되면서 결과만 달라지는 문제까지는 잡아주지 못한다.
그래서 공개 API의 기존 동작을 테스트로 남기고, 변경 때마다 실행하는 회귀 테스트가 필요하다.
여기에 CI를 연결하면 Pull Request마다 swift test가 자동 실행되어, 회귀 버그가 있는 코드가 병합·배포되기 전에 발견된다.
