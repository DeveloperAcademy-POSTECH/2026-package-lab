# 왜 모듈화가 필요합니까?
## 연구 배경

Challenge 4 프로젝트를 진행하면서 프로젝트의 규모가 커질수록 개발 과정에서 여러 한계를 경험했습니다.

### 1. 작은 기능 수정에도 전체 앱 Target을 기준으로 Build와 실행을 시작해야 했습니다.

Camera, DetectModel, VideoEdit과 같은 특정 기능만 수정했음에도 불구하고 항상 전체 App Target을 기준으로 Build와 실행을 시작해야 했습니다.

물론 하나의 Target 안에서도 Swift Compiler는 Incremental Compilation을 수행하여 변경되지 않은 파일의 결과를 재사용할 수 있습니다. 여기서 경험한 문제는 “매번 모든 Swift 파일을 반드시 다시 Compile했다”는 의미가 아니라, Feature별로 독립된 Build 경계와 실행 환경이 없었다는 의미입니다.

특히 DetectModel과 같이 반복적으로 수정하며 결과를 확인해야 하는 기능은 작은 변경에도 전체 App Scheme의 Build와 실행 과정을 거쳐야 했기 때문에 개발 과정에서 많은 시간이 소모되었습니다.

---

### 2. 폴더는 분리되어 있었지만 컴파일 단위는 하나였습니다.

프로젝트를 설계하면서 Feature별로 폴더를 나누고 디자인 패턴을 적용하여 책임을 최대한 분리하려고 노력했습니다.

예를 들어

```
Features
 ├── Camera
 ├── DetectModel
 ├── VideoEdit
 └── Settings
```

와 같이 구조를 나누어 관리하였습니다.

하지만 이러한 분리는 **코드 관리 관점에서의 분리일 뿐**, 컴파일 관점에서는 여전히 하나의 App Target 안에 존재했습니다.

즉,

- Camera만 수정해도
- DetectModel만 수정해도
- VideoEdit만 수정해도

항상 전체 App Target을 기준으로 Build해야 했습니다.

이 과정에서 **"폴더를 나누는 것과 모듈을 나누는 것은 무엇이 다를까요?"**라는 의문이 생겼습니다.

---

### 3. 기능 간 의존성이 점점 복잡해졌습니다.

프로젝트가 커질수록 Feature 간 참조가 자연스럽게 증가했습니다.

새로운 기능을 추가하거나 기존 기능을 수정할 때

- 어느 코드가 영향을 받는지 파악하기 어려워졌고
- 변경 범위를 예측하기 어려워졌습니다.
- 작은 수정이 예상하지 못한 다른 기능에 영향을 줄 가능성도 점점 커졌습니다.


---

### 4. 앞으로 프로젝트는 더 커질 예정이었습니다.

현재 프로젝트에는 Camera, DetectModel, VideoCut 정도의 기능만 존재하지만,

앞으로는

- PoseDetection
- Trick Analysis
- Export
- Recording
- AI Model

등 여러 Feature가 추가될 예정입니다.

현재 구조를 유지한 채 프로젝트 규모만 커진다면

빌드 시간, 의존성 관리, 유지보수 비용은 더욱 증가할 것으로 예상했습니다.

---

이러한 경험을 통해 검색을 통해서 Swift Package Manager 기반의 모듈화를 적용해서 빌드 속도 및 여러 가지 개발 개선을 진행했다는 결과를 보고 Swift Package Manger을 통해서 모듈화를 진행하는 것을 결정했습니다.

하지만 또 다른 의문이 생겼습니다.

> **왜 프로젝트 규모가 커질수록 모듈화가 필요합니까?**

많은 자료에서는 모듈화를 통해 빌드 속도와 개발 생산성이 향상된다고 설명하지만,

- 왜 빌드 속도가 빨라지는지
- 내부적으로 어떤 원리로 동작하는지
- 어떤 문제를 해결하기 위해 이러한 구조가 만들어졌는지

에 대해서는 명확하게 이해할 수 없었습니다.

따라서 이번 연구에서는 **"왜 모듈화가 필요합니까?"** 라는 질문을 시작으로 모듈화의 목적과 동작 원리를 이해하고자 합니다.

# Question 1

## 모듈(Module)은 무엇입니까?

### 왜 이 질문을 했습니까?

모듈화를 공부하면서 가장 먼저 생긴 의문은 **"Module이 정확히 무엇입니까?"**였습니다.

프로젝트를 개발하면서도 Feature별로 폴더를 나누고 디자인 패턴을 적용하며 구조를 관리해왔지만, 많은 자료에서는 "Module을 나누라"는 표현을 사용합니다.

그렇다면 **폴더를 나누는 것과 Module을 나누는 것은 무엇이 다를까요?**

이를 이해하기 위해 먼저 Swift에서 말하는 Module의 의미를 조사하였습니다.

---

# Module의 정의

Swift에서는 Module을 **코드를 배포(Distribution)하고 컴파일(Build)하는 하나의 독립적인 단위**로 정의합니다.

Apple에서는 Module을 다음과 같이 설명합니다.

![[Pasted image 20260803200543.png]]

즉,

- 하나의 Framework
- 하나의 App Target
- 하나의 Library

모두 Swift에서는 하나의 Module이 될 수 있습니다.

---

# Swift에서 Module이란 무엇입니까?

Swift에서 Module은 단순한 폴더가 아닙니다.

Module은

- 함께 컴파일되고
- 하나의 이름으로 import 되며
- Access Control(public, internal 등)의 경계가 되는

**컴파일 단위이자 배포 단위**입니다.

예를 들어

```swift
import Foundation

import SwiftUI

import MyFeature
```

여기서

- Foundation
- SwiftUI
- MyFeature

모두 각각 하나의 Module입니다.

---

# Folder와 Module의 차이

프로젝트를 개발하다 보면 기능별로 폴더를 나누는 경우가 많습니다.

예를 들어

```
Features
 ├── Camera
 ├── DetectModel
 ├── VideoCut
```

이러한 구조는 **코드를 보기 쉽게 정리한 것**일 뿐입니다.

Camera 폴더와 DetectModel 폴더가 존재한다고 해서 각각이 독립적으로 컴파일되는 것은 아닙니다.

만약 모두 하나의 App Target 안에 있다면

```
App Target

├── Camera
├── DetectModel
├── VideoCut
```

컴파일 관점에서는 여전히 하나의 Module입니다.

즉,

Camera만 수정하더라도 Build System은 App Target을 기준으로 Build를 수행합니다.

다만 Swift Compiler는 Module 내부의 Dependency 정보를 이용해 변경된 파일과 영향을 받는 파일만 다시 Compile할 수 있습니다. 폴더만으로는 Feature별 독립 Target 경계가 만들어지지 않는다는 점이 핵심입니다.

---

반면 Swift Package Manager를 이용하면

```
FeatureCamera

FeatureDetectModel

FeatureVideoCut
```

처럼 각각을 독립적인 Module(Target)로 구성할 수 있습니다.

이 경우 각 Module은

- 독립적으로 컴파일되고
- 명시적인 Dependency를 가지며
- import를 통해서만 접근할 수 있습니다. 

---

# 왜 Module이라는 개념이 필요합니까?

Module은 단순히 코드를 나누기 위해 존재하는 것이 아닙니다.

Module은

- 코드의 재사용성을 높이고
- 의존성을 명확하게 관리하며
- 컴파일 범위를 제한하고
- API의 공개 범위를 제어하기 위해 존재합니다.

즉,

Module은 **설계 단위이면서 동시에 컴파일 단위**입니다.

이 점이 Folder와 가장 큰 차이점입니다.

---

# 이번 연구에서 얻은 결론

이번 조사를 통해

처음에는 Module을

> "기능을 나누는 단위"

정도로 생각했지만,

실제로는

> **"컴파일과 접근 제어의 경계를 만드는 단위"**

라는 점을 이해하게 되었습니다.

또한 프로젝트를 폴더로 나누는 것만으로는 컴파일 범위를 분리할 수 없으며,

Swift Package Manager를 이용해 Target을 분리해야 비로소 독립적인 Module이 생성된다는 점을 알게 되었습니다.

### 조사할 내용

# Question 2

## Target은 무엇입니까?

### 왜 이 질문을 했습니까?

모듈(Module)에 대해 조사하면서 또 하나의 의문이 생겼습니다.

Swift Package Manager에서는 Module을 만들기 위해 반드시 **Target**을 정의합니다.

그렇다면

> **Target은 무엇이며 Module과는 어떤 관계입니까?**

이를 이해하기 위해 Target의 역할과 Swift Package에서 어떻게 사용되는지 조사하였습니다.

---

# Target의 정의

Apple에서는 Target을 **빌드 가능한 하나의 단위(Build Unit)** 로 정의합니다.

Swift Package Manager에서는 하나의 Package 안에 여러 Target을 정의할 수 있으며, 각각의 Target은 독립적으로 소스 파일과 의존성을 가집니다.

예를 들어 Package.swift에서는 다음과 같이 Target을 정의합니다.

```swift
let package = Package(
    name: "SkateboardApp",
    targets: [
        .target(
            name: "FeatureCamera"
        ),
        .target(
            name: "FeaturePoseDetection",
            dependencies: ["Core"]
        ),
        .target(
            name: "Core"
        )
    ]
)
```

이 연구에서 사용하는 Swift Source Target은

- 자신만의 Source File을 가지며
- 자신만의 Dependency를 정의하고
- 하나의 Module을 생성합니다.

즉, 이 프로젝트의 범위에서 Target은 **Module을 생성하기 위한 빌드 단위**입니다.

Swift Package에는 Source Target 외에도 Test, Binary, Plugin Target 등이 있으므로 모든 종류의 Target과 Module이 항상 완전히 같은 개념이라고 확대해서는 안 됩니다.

---

# Module과 Target의 관계

처음에는

> Module과 Target이 같은 개념이라고 생각했습니다.

하지만 조사해보니 둘은 같은 의미가 아니었습니다.

| Module | Target |
|---------|---------|
| Swift에서 import 되는 코드 단위 | Build System이 컴파일하는 단위 |
| API와 Access Control의 경계 | Source File과 Dependency를 정의하는 단위 |

Swift Package Manager에서는

```
Target

↓

Compile

↓

Module 생성
```

이라는 관계를 가집니다.

즉,

이 연구에서 사용하는 Swift Source Target을 정의하면 해당 Source 집합은 하나의 Module로 컴파일됩니다. Test Target의 Source는 Test Suite로 컴파일될 수 있으며, Binary·Plugin 등 다른 Target 종류는 역할이 다릅니다.

---

# Target이 필요한 이유

Target은 단순히 코드를 나누기 위한 것이 아닙니다.

Target을 분리하면

- 컴파일 범위를 분리할 수 있고
- Dependency를 명확하게 정의할 수 있으며
- Feature별 독립적인 개발이 가능해집니다.

예를 들어

```
FeatureCamera

↓

FeaturePoseDetection

↓

FeatureVideoEdit
```

처럼 각각을 Target으로 분리하면

각 기능은 필요한 Module만 참조하도록 설계할 수 있습니다.

---

# 이번 연구에서 얻은 결론

Target은 단순한 폴더 구조가 아니라

**컴파일 단위를 정의하는 역할**을 합니다.

또한 Swift Package Manager에서는

Target을 중심으로 Dependency Graph를 구성하고,

이 연구에서 사용하는 Swift Source Target이 하나의 Module을 생성한다는 점을 이해하였습니다.

# Question 3

## 모듈화는 이러한 문제를 어떻게 해결합니까?

### 왜 이 질문을 했습니까?

앞선 내용을 통해 프로젝트 규모가 커질수록 다음과 같은 문제를 경험했습니다.

- Camera, DetectModel, VideoCut과 같은 기능 하나를 수정해도 전체 App Target을 기준으로 Build와 실행을 시작해야 했습니다.
- 기능은 폴더로 분리되어 있었지만 컴파일 관점에서는 하나의 App Target으로 동작했습니다.
- 기능 간 의존성이 점점 복잡해졌습니다.
- 앞으로 더 많은 Feature가 추가될 예정이었습니다.

그렇다면

> **모듈화는 이러한 문제를 어떻게 해결합니까?**

이를 이해하기 위해 모듈화가 제공하는 구조적인 이점을 조사하였습니다.

---

# 1. Dependency를 명확하게 분리합니다.

모놀리식 구조에서는 Feature들이 하나의 Target 안에서 함께 존재합니다.

```
App

├── Camera
├── DetectModel
├── VideoCut
├── Settings
```

이 구조에서는

어떤 Feature가 어떤 Feature를 참조하는지 쉽게 파악하기 어렵고,

프로젝트가 커질수록 Feature 간 의존성이 자연스럽게 증가하게 됩니다.

반면 Swift Package Manager에서는

```
FeatureCamera ───────→ Core
FeatureVideoCut ─────→ Core
FeatureVideoCut ─────→ FeatureCamera
FeatureDetectModel ──→ Core
```

처럼 Target마다 필요한 Dependency를 명시적으로 정의합니다.

예를 들어

```swift
.target(
    name: "FeatureVideoCut",
    dependencies: [
        "Core",
        "FeatureCamera"
    ]
)
```

처럼 Package.swift에서 의존성을 직접 선언합니다.

이러한 구조에서는

- 어떤 Module이 무엇을 사용하는지 명확하게 알 수 있고
- 불필요한 참조를 줄일 수 있으며
- 순환 의존성(Circular Dependency)을 발견하고 의존 방향을 검토하기 쉬워집니다.

다만 SPM이 올바른 의존 방향을 자동으로 설계해 주는 것은 아닙니다. 필요한 Target 관계를 개발자가 정확히 선언하고 순환이 생기지 않도록 설계해야 합니다.

---

# 2. Build 단위를 분리합니다.

이번 연구를 시작하게 된 가장 큰 이유도 Build였습니다.

현재 프로젝트에서는

Camera 기능 하나만 수정하더라도

전체 App Target을 기준으로 Build해야 했습니다. 이때 Swift Compiler는 변경되지 않은 파일의 결과를 재사용할 수 있지만 Feature별 독립 Target 경계는 없습니다.

이는 Feature를 폴더로 나누었을 뿐

컴파일 단위는 여전히 하나였기 때문입니다.

Swift Package Manager에서는

Target마다 독립적인 Build 단위를 가집니다.

```
App

↓

FeatureCamera

↓

FeatureDetectModel

↓

FeatureVideoCut
```

이러한 구조에서는

변경된 Module을 중심으로 Build를 수행할 수 있기 때문에

변경 영향 범위를 줄일 수 있습니다.

다만 여기서 주의해야 할 점은

> **모듈화를 했다고 항상 Build 시간이 줄어드는 것은 아닙니다.**

Build 성능은

- Dependency 구조
- 변경 범위
- Build Cache
- 프로젝트 구성

등 여러 요소의 영향을 받습니다.

이번 연구에서는

왜 변경 범위가 줄어드는지에 집중하여 조사하였습니다.

---

# 3. Access Control을 통한 경계가 생깁니다.

폴더 구조에서는

어떤 코드든 같은 Target 안에 있기 때문에

internal 접근 수준으로도 서로 자유롭게 접근할 수 있습니다.

즉,

Feature 간 경계가 사실상 존재하지 않습니다.

하지만 Module이 분리되면

Module 밖에서는

public으로 공개한 API만 접근할 수 있습니다.

예를 들어

```
FeatureCamera

↓

public CameraService

internal CameraRepository
```

라면

다른 Module에서는

CameraRepository에는 접근할 수 없고

CameraService만 사용할 수 있습니다.

즉,

Module은

컴파일 단위일 뿐 아니라

API의 경계를 정의하는 역할도 수행합니다.

---

# 4. Feature 단위 개발이 가능해집니다.

현재 프로젝트에서는

DetectModel 기능만 수정하더라도

앱 전체를 실행하여 결과를 확인해야 했습니다.

하지만 Feature를 Module로 분리하면

Feature별 Example App을 구성할 수 있습니다.

예를 들어

```
FeatureCameraExample

FeatureDetectModelExample

FeatureVideoCutExample
```

각 Feature를 독립적으로 실행하고 테스트할 수 있습니다.

이러한 구조는

- 개발 속도 향상
- 기능별 테스트
- 병렬 개발

등의 장점을 제공합니다.

특히 반복적인 수정과 검증이 필요한

DetectModel과 같은 기능에서는

개발 피드백 루프를 줄이는 데 도움이 될 것으로 기대합니다.

# 이번 연구에서 얻은 결론

이번 조사를 통해

모듈화의 목적은 단순히 코드를 보기 좋게 나누는 것이 아니라는 점을 이해하였습니다.

모듈화는

- Dependency를 명확하게 관리하고
- Build 범위를 제한하며
- Module 간 API 경계를 만들고
- Feature 단위의 독립적인 개발 환경을 제공하기 위한 설계 방식입니다.

즉,

모듈화는 **프로젝트가 커질수록 증가하는 복잡성을 관리하기 위한 구조적인 해결 방법**이라고 이해할 수 있었습니다.

하지만 여전히 하나의 의문이 남았습니다.

> **왜 Module을 분리하면 변경 범위가 줄어들고, Build는 어떤 원리로 필요한 부분만 다시 컴파일할 수 있을까요?**

다음 연구에서는 Swift의 Build Process와 Incremental Build의 동작 원리를 조사하고자 합니다.

---

## Question 4

# 왜 Build 시간이 줄어들 수 있습니까?

### 왜 이 질문을 했습니까?

모듈화를 도입하려는 이유 중 하나는 빌드 속도와 개발 피드백 루프를 개선하기 위해서였습니다.

현재 프로젝트에서는 Camera, DetectModel, VideoCut과 같은 기능이 모두 하나의 App Target 안에 존재합니다. 특정 기능만 수정하고 검증하고 싶어도 전체 App Target을 기준으로 빌드와 실행이 이루어집니다.

앞선 조사를 통해 Target을 분리하면 소스 코드와 의존성을 독립된 단위로 구성할 수 있다는 점을 이해했습니다. Apple의 PackageDescription 문서에 따르면 Target의 Source File 집합은 Module 또는 Test Suite로 컴파일됩니다. 이 연구에서 사용하는 Library Source Target은 각각 하나의 Module을 만듭니다.

그렇다면 다음과 같은 의문이 생깁니다.

> **Target과 Module을 분리하면 왜 Build 시간이 줄어들 수 있을까요?**

이를 이해하기 위해 Build Process, Dependency Graph, Incremental Build의 관계를 조사하였습니다.

---

## 1. Build는 어떤 과정으로 진행됩니까?

애플리케이션의 Build는 단순히 Swift 파일을 실행 파일로 변환하는 하나의 작업이 아닙니다.

개념적으로 다음과 같은 단계를 거칩니다.

```text
Source Code
    ↓
Dependency 분석
    ↓
Compile
    ↓
Object File / Module 생성
    ↓
Link
    ↓
Executable 또는 Library 생성
```

### Compile

Compile은 Swift Source Code를 컴퓨터가 처리할 수 있는 중간 결과물로 변환하는 과정입니다.

Swift Compiler는 Target에 속한 소스 코드를 분석하고 컴파일하여 Module과 Object File 등의 빌드 결과물을 생성합니다.

Swift Package Manager의 Target은 소스 파일 집합과 의존성을 정의하며, 이 소스 파일들은 하나의 Module 또는 Test Suite로 컴파일됩니다.

### Link

Compile 과정에서 생성된 Object File과 Library를 결합하여 최종 실행 파일이나 Library를 생성하는 과정을 Link라고 합니다.

즉, 소스 파일을 컴파일했다고 해서 바로 실행 가능한 앱이 만들어지는 것은 아닙니다. App Target과 각 Library 또는 Framework의 결과물이 최종적으로 연결되어야 합니다.

---

## 2. Dependency Graph는 무엇입니까?

프로젝트에는 Target과 Module 사이의 의존 관계가 존재합니다.

예를 들어 다음 구조를 생각할 수 있습니다.

```text
SkateboardApp
├── FeatureCamera
│   └── Core
├── FeatureDetectModel
│   ├── Core
│   └── SharedModel
└── FeatureVideoCut
    └── Core
```

이 구조에서 다음과 같은 의존 관계가 만들어집니다.

```text
SkateboardApp
    ├── FeatureCamera
    ├── FeatureDetectModel
    └── FeatureVideoCut

FeatureCamera ───────→ Core
FeatureDetectModel ──→ Core
FeatureDetectModel ──→ SharedModel
FeatureVideoCut ─────→ Core
```

이처럼 각 Target이 어떤 Target 또는 Product에 의존하는지를 그래프 형태로 표현한 것을 Dependency Graph라고 볼 수 있습니다.

Swift Package의 Target은 같은 Package 안의 다른 Target이나 외부 Package가 제공하는 Product에 의존할 수 있습니다. 이 의존성은 `Package.swift`에서 명시적으로 선언됩니다.

```swift
.target(
    name: "FeatureDetectModel",
    dependencies: [
        "Core",
        "SharedModel"
    ]
)
```

Xcode Build System은 이러한 의존 관계를 분석하여 어떤 작업이 먼저 수행되어야 하는지, 어떤 작업을 병렬로 수행할 수 있는지를 판단합니다. Apple은 Target 간 의존성과 구성 정보를 **정확하게** 제공하면 Build System이 올바르게 작업을 생략하고 병렬화할 수 있다고 설명합니다.

---

## 3. Incremental Build는 무엇입니까?

개발자는 매번 프로젝트를 완전히 새로 빌드하지 않습니다.

일반적인 개발 과정에서는 코드를 일부 수정한 뒤 다시 Build합니다. 이때 Build System과 Compiler는 이전 빌드 결과를 활용하여 다시 수행해야 하는 작업을 판단합니다.

이처럼 변경 사항을 기준으로 필요한 부분만 다시 빌드하려는 방식을 Incremental Build라고 합니다.

개념적으로 다음과 같이 비교할 수 있습니다.

### Clean Build

```text
기존 Build 결과 제거
    ↓
모든 Target 및 Source 다시 Compile
    ↓
모든 결과 다시 Link
```

### Incremental Build

```text
코드 일부 수정
    ↓
변경된 파일과 Dependency 분석
    ↓
영향을 받는 Build 작업 수행
    ↓
필요한 결과 다시 Link
```

Apple은 Incremental Build 성능을 개선하기 위해 Build System에 Target 간 의존성을 정확히 알려주고, 각 빌드 주기에서 Compiler가 수행하는 작업량을 줄여야 한다고 설명합니다.

따라서 Incremental Build의 핵심은 단순히 파일 수정 시간을 확인하는 것이 아니라 다음을 판단하는 데 있습니다.

- 무엇이 변경되었습니까?
    
- 변경된 코드에 의존하는 코드는 무엇입니까?
    
- 기존 Build 결과 중 무엇을 재사용할 수 있습니까?
    
- 어떤 Compile 또는 Link 작업을 다시 수행해야 합니까?
    

---

## 4. 모듈화하면 왜 변경 범위가 줄어들 수 있습니까?

### 하나의 Target인 경우

다음과 같이 모든 기능이 하나의 App Target 안에 있다고 가정합니다.

```text
App Target
├── Camera
├── DetectModel
├── VideoCut
└── Settings
```

폴더는 분리되어 있지만 모든 파일은 하나의 Target과 Module 안에 존재합니다.

DetectModel의 코드를 수정했을 때 Swift Compiler는 같은 Module 안에서 영향을 받는 소스 파일을 분석하고 필요한 Compile 작업을 수행합니다.

여기서 주의해야 할 점은 다음과 같습니다.

> 하나의 Target이라고 해서 매번 모든 Swift 파일이 반드시 다시 컴파일된다고 단정할 수는 없습니다.

Swift Compiler도 Module 내부의 Dependency 정보를 활용해 Incremental Compilation을 수행할 수 있습니다. 따라서 “모놀리식 Target은 항상 전체 파일을 다시 컴파일한다”는 표현은 정확하지 않습니다.

다만 하나의 Module 안에서 코드 간 결합이 높고 변경 영향이 넓다면, Compiler가 다시 처리해야 하는 범위도 커질 수 있습니다.

### 여러 Target으로 분리한 경우

```text
SkateboardApp
├── FeatureCamera
├── FeatureDetectModel
├── FeatureVideoCut
└── Core
```

각 Feature를 독립된 Target으로 분리하면 Target마다 Source와 Dependency의 경계가 생깁니다.

예를 들어 `FeatureDetectModel`이 변경되었고 다른 Feature가 그 변경에 영향을 받지 않는다면, 이미 생성된 다른 Module의 Build 결과를 재사용할 가능성이 생깁니다.

```text
FeatureDetectModel 수정
    ↓
FeatureDetectModel Compile
    ↓
의존 관계에 따라 영향받는 작업 수행
    ↓
App Link
```

반면 변경되지 않은 독립 Module은 기존 Build 결과를 재사용할 수 있습니다.

따라서 모듈화의 Build 관점 핵심은 다음과 같습니다.

> **프로젝트 전체를 무조건 더 빠르게 만드는 것이 아니라, 변경과 재빌드의 영향을 일정한 경계 안으로 제한할 가능성을 만드는 것입니다.**

---

## 5. Build 작업의 병렬성을 높일 수 있습니다.

Target 간 의존성이 명확하고 서로 독립되어 있다면 Build System은 일부 Target을 동시에 빌드할 수 있습니다.

```text
                   ┌─ FeatureCamera ───────┐
Core ──────────────┼─ FeatureDetectModel ──┼─ App
                   └─ FeatureVideoCut ─────┘
```

`FeatureCamera`, `FeatureDetectModel`, `FeatureVideoCut`이 서로 직접 의존하지 않고 공통으로 `Core`만 의존한다면, `Core`가 준비된 이후 세 Feature의 Compile 작업을 병렬로 수행할 가능성이 있습니다.

반면 Target 간 의존성이 일렬로 연결되어 있다면 병렬로 실행하기 어렵습니다.

```text
Core
  ↓
FeatureCamera
  ↓
FeatureDetectModel
  ↓
FeatureVideoCut
  ↓
App
```

Apple은 Xcode Build System이 Target의 Build Phase와 의존 관계를 분석하여 병렬로 수행할 수 있는 작업을 결정한다고 설명합니다. 따라서 Target을 많이 만드는 것보다 **불필요한 의존성을 줄이고 독립적인 구조를 만드는 것**이 중요합니다.

---

## 6. Feature Example App으로 검증 범위를 줄일 수 있습니다.

모듈화로 얻을 수 있는 개발 생산성은 Compile 시간에만 한정되지 않습니다.

현재 프로젝트에서는 DetectModel 하나를 검증하려 해도 다음 과정이 필요합니다.

```text
SkateboardApp 전체 Build
    ↓
앱 실행
    ↓
영상 선택 또는 Camera 진입
    ↓
DetectModel 동작 확인
```

Feature별 Example App을 구성하면 다음과 같이 검증할 수 있습니다.

```text
DetectModelExample Build
    ↓
테스트 영상 입력
    ↓
DetectModel 결과 확인
```

Example App은 메인 애플리케이션보다 적은 Target과 기능만 포함하도록 구성할 수 있습니다. 따라서 검증에 필요하지 않은 화면과 기능을 실행하지 않고 특정 Feature에 집중할 수 있습니다.

이는 Compiler의 Incremental Build 원리 자체와는 구분해야 합니다.

- Module 분리: Compile 및 Dependency의 경계를 만듭니다.
    
- Example App: 개발자가 실행하고 검증해야 하는 애플리케이션의 범위를 줄입니다.
    

두 방법 모두 개발 피드백 루프를 짧게 만들 수 있지만, 서로 다른 방식으로 생산성을 개선합니다.

---

## 7. 모듈화를 하면 Build가 반드시 빨라집니까?

그렇지 않습니다.

모듈화를 적용했다고 해서 Clean Build와 Incremental Build가 반드시 모두 빨라진다고 단정할 수 없습니다.

Build 시간은 다음과 같은 요소의 영향을 받습니다.

- Target과 Module의 개수
    
- Target 간 Dependency 구조
    
- 변경된 API의 범위
    
- Compile 작업의 병렬성
    
- Source Code의 복잡도
    
- Generic 및 Type Inference 사용 형태
    
- Link 방식
    
- Build Cache 사용 여부
    
- 사용 중인 Xcode 및 Swift Compiler 버전
    
- 개발 장비의 CPU 및 Memory
    

Target이 많아지면 Build System의 Dependency Graph 구성과 여러 Module의 계획·생성 비용이 늘어날 수 있습니다. 반대로 독립 작업의 병렬성이 좋아질 수도 있으므로 Target 수만으로 Build 시간을 예측할 수는 없습니다.

따라서 다음 문장은 일반적인 사실로 단정하기 어렵습니다.

> “모듈화를 하면 Build 시간이 무조건 줄어듭니다.”

실제 프로젝트에서 같은 조건으로 측정하기 전에는 단정할 수 없습니다.

더 정확한 표현은 다음과 같습니다.

> **적절한 모듈화는 Dependency와 변경 범위를 제한하고 Build 작업의 병렬성과 기존 결과의 재사용 가능성을 높여 Incremental Build 시간을 줄이는 데 도움이 될 수 있습니다.**

프로젝트별 실제 효과는 동일한 조건에서 측정해야 합니다.

## 작은 실험: 모듈화 전후 Build 범위 비교

### 실험 목적

모듈화가 Build 시간을 무조건 줄이는지 증명하는 것이 아니라 다음을 관찰합니다.

1. 코드를 변경했을 때 어떤 Target이 다시 빌드됩니까?
    
2. Target 간 의존 방향에 따라 영향 범위가 어떻게 달라집니까?
    
3. Feature Example App이 검증 범위를 줄입니까?
    

### 실험 구조 A: 하나의 App Target

```text
MonolithicApp
├── Camera
├── DetectModel
├── VideoCut
└── Settings
```

### 실험 구조 B: Feature Target 분리

```text
ModularApp
├── FeatureCamera
├── FeatureDetectModel
├── FeatureVideoCut
└── Core
```

### 실험 절차

#### 1단계: Clean Build 측정

두 프로젝트에서 각각 다음 작업을 수행합니다.

```text
Product
→ Clean Build Folder
→ Build
```

기록할 항목:

|항목|Monolithic|Modular|
|---|--:|--:|
|Clean Build 1회|||
|Clean Build 2회|||
|Clean Build 3회|||
|평균|||

첫 번째 Build는 Cache와 시스템 상태의 영향을 받을 수 있으므로 가능하면 3회 이상 측정합니다.

#### 2단계: 구현 내부 변경

`DetectModel`의 `private` 또는 `internal` 구현만 수정합니다.

예시:

```swift
func detect() -> DetectionResult {
    // 구현 내부의 계산 또는 로그 수정
}
```

그 후 Build하고 다음을 기록합니다.

- 다시 Compile된 파일
    
- 다시 Build된 Target
    
- Build 시간
    
- Link 작업 수행 여부
    

#### 3단계: 공개 API 변경

`FeatureDetectModel`이 외부에 공개하는 API를 변경합니다.

```swift
public func detect() -> DetectionResult
```

에서 다음과 같이 변경할 수 있습니다.

```swift
public func detect(options: DetectionOptions) -> DetectionResult
```

그 후 `FeatureDetectModel`에 의존하는 Target이 다시 Build되는지 확인합니다.

#### 4단계: Dependency 방향 비교

다음 두 구조를 비교합니다.

```text
구조 A

FeatureCamera
    ↓
FeatureDetectModel
    ↓
FeatureVideoCut
```

```text
구조 B

FeatureCamera ────────┐
FeatureDetectModel ───┼──→ Core
FeatureVideoCut ──────┘
```

구조 A는 의존성이 연쇄적으로 연결되고, 구조 B는 Feature 간 직접 의존성을 줄인 구조입니다.

각 구조에서 하위 Module의 API를 변경하고 다시 Build되는 Target을 기록합니다.

### 실험에서 캡처할 화면

- Xcode Build Report
    
- Build Timeline
    
- Target별 Compile 작업
    
- `Package.swift`의 Target Dependency
    
- 모듈화 전후 구조
    
- Example App Scheme
    

### 예상 관찰

다음은 가설이며, 실제 실험 전에는 결과로 단정하면 안 됩니다.

- 구현 내부 변경은 공개 API 변경보다 영향 범위가 작을 수 있습니다.
    
- 의존성이 적은 Target은 변경의 영향을 덜 받을 수 있습니다.
    
- 일렬로 연결된 Dependency Graph는 Build 병렬성을 제한할 수 있습니다.

- 직렬 Dependency Graph는 Target 수준의 Build 병렬성을 제한했습니다.
- 이 Sample의 Modular Clean Build는 Monolithic보다 느렸습니다.

## 이번 연구에서 얻은 결론

모듈화가 Build 시간을 줄이는 이유를 단순히 다음과 같이 설명해서는 안 됩니다.

> “Target이 나뉘면 변경된 Target만 빌드하기 때문입니다.”

실제로는 Dependency Graph, 변경된 코드의 종류, 공개 API의 변화, Compiler의 Incremental Compilation, Link 과정 등이 함께 영향을 줍니다.

이번 조사에서 얻은 더 정확한 결론은 다음과 같습니다.

> **모듈화는 Build의 경계를 만들고 Dependency를 명시하여, Build System이 변경의 영향을 더 제한된 범위에서 판단할 수 있도록 돕습니다.**

따라서 모듈화의 핵심 가치는 단순한 Build 시간 감소가 아니라 다음에 있습니다.

- 변경 영향 범위를 제한합니다.
    
- 기존 Build 결과를 재사용할 가능성을 높입니다.
    
- 의존성이 없는 Target 작업의 병렬 Build 가능성을 높일 수 있습니다.
    
- Feature Example App을 통해 실행 및 검증 범위를 줄입니다.
    
- 개발 피드백 루프를 짧게 만들 수 있습니다.
    

이번 Sample에서는 Clean Build가 더 느렸고, 공개 API 변경과 의존성 방향에서는 독립 Module 구조가 변경 범위를 줄였습니다. 다른 프로젝트에서도 같은 결과가 나온다고 일반화할 수는 없으므로 각 프로젝트의 실제 코드와 개발 환경에서 다시 측정해야 합니다.

# Question 5

## 모듈화를 하면 항상 좋습니까?

### 왜 이 질문을 했습니까?

앞선 조사에서는 모듈화를 통해 다음과 같은 이점을 얻을 수 있음을 확인하였습니다.

- Dependency를 명시할 수 있습니다.
    
- Build와 API의 경계를 만들 수 있습니다.
    
- 변경 영향 범위를 제한할 수 있습니다.
    
- Feature 단위의 개발과 검증이 가능합니다.
    

그렇다면 가능한 한 많은 Module을 만드는 것이 가장 좋은 구조일까요?

> **Module을 많이 나눌수록 프로젝트의 생산성과 유지보수성이 계속 향상될까요?**

이를 확인하기 위해 모듈화로 인해 발생할 수 있는 비용과 적절한 Module 분리 기준을 함께 조사하였습니다.

---

## 1. Module이 많아질수록 관리해야 할 대상도 늘어납니다.

각 Module은 단순한 폴더가 아닙니다.

하나의 Target으로 분리하면 다음 항목을 관리해야 할 수 있습니다.

- Target 이름과 Source 경로
    
- Target Dependency
    
- Product 구성
    
- Access Level
    
- Resource
    
- Test Target
    
- Build Setting
    
- Deployment Target
    
- Package 및 버전 호환성
    
- Module 간 API
    

예를 들어 기능마다 매우 작은 Module을 만들면 다음과 같은 구조가 될 수 있습니다.

```text
FeatureCameraUI
FeatureCameraModel
FeatureCameraService
FeatureCameraPermission
FeatureCameraPreview
FeatureCameraNavigation
```

기술적으로 분리할 수 있더라도 각 Module의 책임과 API를 별도로 관리해야 합니다.

따라서 Module 수가 증가하면 Package Manifest, Dependency Graph, Test 구성과 API 설계의 관리 비용도 함께 증가할 수 있습니다.

---

## 2. 잘못 분리하면 Dependency가 더 복잡해질 수 있습니다.

모듈화의 목적은 Dependency를 명확하게 만드는 것입니다.

하지만 경계를 잘못 설계하면 Module 간 Dependency가 오히려 복잡해질 수 있습니다.

```text
FeatureCamera
    ↓
FeatureVideoCut
    ↓
FeatureDetectModel
    ↓
FeatureCamera
```

이와 같이 의존 그래프에 Loop가 생기면 순환 의존이 됩니다. Target 간 의존성을 명시적으로 선언하면 관계가 가시화되지만 의존 방향은 개발자가 설계해야 합니다. 순환 의존은 Package 해석 또는 Build 실패로 이어질 수 있습니다.

Swift Package Manager에서는 Target의 Dependency를 명시적으로 선언해야 합니다. 한 Target은 같은 Package의 다른 Target이나 외부 Package의 Product에 의존할 수 있습니다.

명시적인 선언은 Dependency를 확인하기 쉽게 만들지만, Dependency 구조를 자동으로 좋게 만들어주는 것은 아닙니다.

즉, SPM은 의존성을 표현하는 도구이며 올바른 의존 방향은 개발자가 설계해야 합니다.

---

## 3. Module 간 API 설계 비용이 발생합니다.

하나의 Module 안에서는 `internal`로 선언된 타입과 함수에 접근할 수 있습니다.

그러나 Module을 분리하면 다른 Module이 사용해야 하는 API를 외부에 공개해야 합니다.

```swift
public protocol DetectionService {
    func detect(video: VideoInput) async throws -> DetectionResult
}
```

이 과정에서 다음을 결정해야 합니다.

- 어떤 기능을 외부에 공개할 것입니까?
    
- 구현 세부 사항을 어떻게 숨길 것입니까?
    
- 어떤 데이터 타입을 Module 경계 밖으로 전달할 것입니까?
    
- API 변경 시 하위 호환성을 고려해야 합니까?
    
- 공통 타입을 어느 Module에 둘 것입니까?
    

이러한 고민은 장기적으로 구조를 명확하게 만들 수 있지만, 초기 개발 비용을 증가시킵니다.

또한 필요 이상으로 많은 API를 `public`으로 공개하면 Module의 캡슐화가 약해지고 변경하기 어려운 인터페이스가 늘어날 수 있습니다.

---

## 4. 공통 Module이 지나치게 커질 수 있습니다.

Feature 간 직접 의존성을 없애기 위해 모든 공통 코드를 `Core` 또는 `Shared` Module에 넣기 시작하면 새로운 문제가 발생할 수 있습니다.

```text
Core
├── CameraModel
├── VideoModel
├── DetectionModel
├── UIComponent
├── Navigation
├── Logging
├── FileStorage
└── Utility
```

모든 Feature가 하나의 거대한 Core에 의존하면 다음 문제가 발생할 수 있습니다.

- Core 변경의 영향 범위가 커집니다.
    
- 모든 Feature가 불필요한 코드를 함께 참조합니다.
    
- Core가 많은 변경과 의존성이 집중되는 중심점이 되어 Monolith와 유사한 역할을 할 위험이 있습니다.
    
- 책임과 경계가 다시 불분명해집니다.
    

따라서 “Feature 간 의존성을 없애기 위해 모든 것을 Shared에 넣는 방식”은 올바른 해결이라고 보기 어렵습니다.

공통 Module도 책임과 변경 이유를 기준으로 나눌 필요가 있습니다.

---

## 5. Clean Build 비용이 증가할 수도 있습니다.

이 연구에서처럼 Source Target으로 Module을 분리하면 각 Module의 Dependency를 분석하고 Build를 계획하는 작업이 필요합니다.

의존성이 없는 Target 작업을 병렬로 실행할 가능성이 있지만, Module 수가 많아질수록 Build 계획과 Module별 Compile 작업도 증가할 수 있습니다. 두 효과 중 어느 쪽이 더 큰지는 그래프, 코드, 장비에 따라 달라집니다.

따라서 다음과 같은 결과가 나올 가능성이 있습니다.

- 특정 변경에서 Incremental Build가 개선될 수 있습니다.
    
- 특정 조건에서는 Clean Build가 비슷하거나 더 느려질 수 있습니다.
    
- 특정 API 변경에서는 많은 하위 Target이 다시 Build될 수 있습니다.
    
- Module Planning 비용이 증가할 수 있습니다.
    

정확한 결과는 프로젝트 구조, Xcode 버전, Compiler 및 개발 환경에 따라 달라집니다.

실제 프로젝트를 측정하기 전에는 단정할 수 없습니다.

모듈화의 효과는 Clean Build 하나만으로 평가하기보다 다음을 함께 측정해야 합니다.

- Clean Build
    
- Incremental Build
    
- 공개 API 변경 후 Build
    
- 구현 내부 변경 후 Build
    
- Feature Example App Build
    
- 개발자가 기능을 수정하고 검증하기까지 걸리는 전체 시간
    

---

## 6. 프로젝트 탐색이 어려워질 수 있습니다.

작은 프로젝트는 하나의 Target 안에서도 충분히 이해할 수 있습니다.

그러나 Module을 지나치게 잘게 나누면 간단한 기능의 동작을 파악하기 위해 여러 Package와 Target을 이동해야 할 수 있습니다.

```text
FeatureCamera
    ↓
CameraInterface
    ↓
CameraImplementation
    ↓
CameraModel
    ↓
MediaFoundation
    ↓
SharedTypes
```

이러한 구조는 큰 조직이나 명확한 교체 가능성이 필요한 시스템에서는 의미가 있을 수 있습니다.

하지만 작은 팀과 초기 프로젝트에서는 오히려 다음 비용이 생길 수 있습니다.

- 코드 탐색 시간이 증가합니다.
    
- 기능의 전체 흐름을 이해하기 어렵습니다.
    
- 새로운 팀원이 구조를 학습하는 데 시간이 필요합니다.
    
- 간단한 변경에도 여러 Module을 수정해야 합니다.

## 7. 언제 Module을 분리해야 합니까?

모든 프로젝트에 적용되는 하나의 절대적인 기준은 확인할 수 없습니다.

모든 프로젝트에 공통으로 적용되는 절대적인 기준은 확인하기 어렵습니다.

대신 다음 질문을 기준으로 Module 분리를 판단할 수 있습니다.

### 독립적으로 변경됩니까?

Camera와 DetectModel처럼 서로 다른 이유로 자주 변경되는 기능이라면 경계를 분리할 가치가 있습니다.

### 독립적으로 실행하거나 검증할 필요가 있습니까?

DetectModel이나 VideoCut처럼 반복적으로 수정하고 결과를 확인해야 한다면 Feature Module과 Example App이 도움이 될 수 있습니다.

### Dependency 방향을 제한해야 합니까?

특정 Feature가 다른 Feature의 구현에 직접 접근하지 못하도록 강제해야 한다면 Module 경계가 유용합니다.

### 여러 곳에서 재사용됩니까?

Logging, Media Processing, Shared Model처럼 여러 Feature에서 사용되는 기능이라면 독립 Module을 고려할 수 있습니다.

다만 단순히 두 곳에서 사용된다는 이유만으로 무조건 공통 Module로 분리해서는 안 됩니다. 두 코드가 앞으로 같은 이유로 변경되는지도 함께 판단해야 합니다.

### 별도의 테스트 경계가 필요합니까?

특정 기능을 다른 Feature와 독립적으로 테스트해야 한다면 Test Target을 포함한 Module 분리가 도움이 됩니다.

### 팀이 독립적으로 작업해야 합니까?

여러 팀원이나 팀이 기능별로 병렬 개발해야 한다면 책임과 Dependency가 명확한 Module 경계가 유용합니다.

## 8. Skateboard App에는 어떻게 적용할 것입니까?

현재 프로젝트에서는 다음과 같은 Feature가 존재하거나 추가될 예정입니다.

```text
SkateboardApp
├── Camera
├── DetectModel
├── VideoCut
├── PoseDetection
├── VideoEdit
└── Settings
```

처음부터 모든 세부 기능을 Module로 나누기보다, 독립적으로 개발하고 검증할 필요가 큰 Feature부터 분리할 수 있습니다.

### 1단계 제안

```text
SkateboardApp
├── FeatureCamera
├── FeatureAnalysis
├── FeatureVideoEdit
└── Core
```

### FeatureCamera

- Camera 권한
    
- Preview
    
- Recording
    
- 영상 입력 생성
    

### FeatureAnalysis

- DetectModel
    
- PoseDetection
    
- 시도 구간 판별
    
- 분석 결과 생성
    

### FeatureVideoEdit

- VideoCut
    
- Clip 생성
    
- Export
    

### Core

- 정말 여러 Feature가 공유하는 최소한의 타입과 서비스
    
- Logging
    
- File 또는 Media 관련 공통 추상화
    

이 구조를 출발점으로 삼고 실제 Dependency와 변경 패턴을 관찰하면서 Module을 추가로 분리할 수 있습니다.

## 9. 처음부터 완벽한 Module 경계를 만들 필요는 없습니다.

Module 경계는 프로젝트가 성장하면서 조정될 수 있습니다.

처음부터 모든 미래 요구사항을 예측하여 복잡한 구조를 만들면 현재 필요보다 큰 비용을 지불할 수 있습니다.

따라서 다음과 같은 점진적인 접근이 적절합니다.

```text
현재 가장 큰 문제 확인
    ↓
독립성이 높은 Feature 하나 분리
    ↓
Dependency와 Build 결과 측정
    ↓
개발 경험 평가
    ↓
다음 Module 분리 여부 결정
```

현재 프로젝트에서는 반복 검증 비용이 큰 `DetectModel` 또는 `PoseDetection`을 우선 분리 대상으로 선택할 수 있습니다.

그 후 다음을 확인합니다.

- 독립적인 Example App을 만들 수 있습니까?
    
- App과 Feature의 Dependency가 명확해졌는가?
    
- Build 및 검증 시간이 실제로 줄었습니까?
    
- 공개 API 설계 비용이 감당할 만합니까?
    
- 새로운 Module이 다른 Feature와 과도하게 연결되지는 않습니까?

## 이번 연구에서 얻은 결론

모듈화는 프로젝트가 커질수록 발생하는 Dependency와 변경 복잡성을 관리하는 강력한 방법입니다.

하지만 Module을 많이 만드는 것 자체가 목표가 되어서는 안 됩니다.

지나친 모듈화는 다음 비용을 만들 수 있습니다.

- Target 및 Dependency 관리 증가
    
- Module 간 API 설계 비용
    
- Package 구조 탐색 비용
    
- Build 계획 및 Module 생성 비용
    
- 공통 Module 비대화
    
- 복잡한 Dependency Graph
    

따라서 좋은 모듈화는 다음과 같이 정의할 수 있습니다.

> **코드를 최대한 많이 나누는 것이 아니라, 서로 다른 책임과 변경 이유를 가진 영역 사이에 필요한 경계를 만드는 것**

현재 Skateboard App에서는 모든 기능을 한 번에 분리하기보다 독립적인 개발과 반복 검증의 필요성이 높은 Feature부터 점진적으로 분리하는 것이 적절합니다.

# 최종 결론

이번 연구는 다음 질문에서 시작하였습니다.

> **왜 프로젝트가 커질수록 모듈화가 필요합니까?**

조사를 통해 Module은 단순한 폴더가 아니라 Compile, Dependency, Access Control의 경계라는 점을 이해하였습니다.

Swift Package Manager의 Target은 Source와 Dependency를 정의하고, 그 결과 Module을 생성하는 빌드 단위입니다.

모듈화는 다음 문제를 해결하는 데 도움을 줄 수 있습니다.

- Feature 간 Dependency를 명시합니다.
    
- 변경 영향 범위를 제한합니다.
    
- Access Control을 통해 API 경계를 만듭니다.
    
- Feature 단위의 개발과 검증을 가능하게 합니다.
    
- 의존성이 없는 Target 작업의 병렬 Build 가능성을 높일 수 있습니다.
    
- 개발 피드백 루프를 줄일 수 있습니다.
    

하지만 모듈화가 Build 시간을 반드시 줄여주거나 프로젝트 구조를 자동으로 개선하는 것은 아닙니다.

모듈화의 효과는 Module의 개수보다 다음 요소에 의해 결정됩니다.

- Module 경계가 책임에 맞게 나뉘어 있습니까?
    
- Dependency 방향이 명확합니까?
    
- Feature가 독립적으로 변경되고 검증될 수 있습니까?
    
- 공통 Module이 지나치게 커지지 않았습니까?
    
- 구조의 복잡성보다 얻는 이점이 더 큽니까?
    

따라서 현재 내린 결론은 다음과 같습니다.

> **모듈화는 빌드 속도를 높이기 위한 단순한 기법이 아니라, 프로젝트가 성장하면서 증가하는 변경과 의존성의 영향을 제어하기 위한 설계 방법입니다.**
